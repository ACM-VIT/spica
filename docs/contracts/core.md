# Spica core contract v1

Status: **specification for review, not an implemented API or runtime**. Task [001](../tasks/001-contracts.md) owns this contract. Architecture and authority come from [architecture](../ARCHITECTURE.md) and [provider design](../PROVIDERS_AND_ORCHESTRATION.md). [Reference evidence](references.md) pins upstream behavior; upstream behavior does not override this contract. [Scenarios](scenarios.md) are future regression oracles, not passing tests.

## 1. Authority and identifiers

The domain is the single writer of durable intent, execution state, app task relationships, approvals, effect journal and review records. Storage commits these atomically behind its boundary. Adapters own runtime processes/transports, protocol correlation and upstream mappings, not application policy. Runtimes execute their native tools. The UI and extensions consume queries/subscriptions and submit commands; a view, script reload or subscription never owns a run. No UI is required for progress.

IDs are opaque, globally unique, immutable, never reused, and not filesystem paths or provider labels. Public values are strings; storage encoding is private. Domain allocates IDs once in the accepting transaction, except caller-generated command IDs. All references are typed: ProjectId, ThreadId, RunId, MessageId, TaskId, WorkspaceId, RuntimeInstanceId, RuntimeSessionId, ApprovalId, EffectId, ReviewId, WaiterId. An upstream string cannot substitute for an app ID.

| Entity | Identity and lifetime |
| --- | --- |
| Project | ProjectId identifies an app project; names/root paths can change without changing identity. |
| Thread | ThreadId belongs to one project and workspace binding; owns ordered persistent messages and runs. Switching views cannot rebind an active run. |
| Run | RunId is one submitted generation attempt in one thread, with one immutable execution selection. A new attempt has a new ID; resume/reconcile is not a new attempt. At most one nonterminal run per thread in v1. |
| Message | MessageId identifies one original user/assistant/tool message; content blocks have stable local block IDs and append offsets. Assistant messages can be incomplete. Tool calls have separate correlated call IDs. |
| Task | TaskId identifies an app-owned work packet and parent/child edge, not a runtime-native child. A task can have sequential runs; dispatch and repair attempts remain distinct and attributable. |
| Runtime | RuntimeInstanceId identifies an adapter-managed runtime incarnation, kind and exact version/schema. RuntimeSessionId is an app ID mapped to opaque upstream session/thread IDs and account/workspace. Reconnection may create a new instance bound to the same session; it never silently creates a replacement session. |

Each run persists `selection = {runtime_kind, required_runtime_version, session_id?, model_provider, model_id, effort, account_ref, workspace_id, capability_revision}`. Requested and effective selections are separate fields. Account references are opaque nonsecret handles; auth material remains with the supported runtime/auth boundary. A runtime name (Codex/OpenCode) is not a model provider or model. Effort is an explicit supported value or `not_applicable`, never guessed from labels. Unknown effective identity remains unknown. Before dispatch, unsupported selection rejects; an observed unexpected model/provider/account/effort fallback stops further dispatch and requests cancellation of active work, records `selection_mismatch`, and cannot become ordinary success. No automatic alternate-model retry.

## 2. Workspace ownership and candidates

WorkspaceId denotes a registered execution location: canonical root, filesystem identity where available, repository identity, checkout/worktree identity, expected branch and base revision (or explicit non-Git mode). Paths alone are insufficient. Each dispatch revalidates binding against this record; mismatch blocks effects. A workspace binding is immutable on a run; changing it requires a new command/run. Reopening never uses the currently selected UI directory.

Task packets include purpose, parent/task IDs, owned paths or explicit private worktree, workspace/branch/base, selection, acceptance scenarios, finite budgets, evidence/result location and owner. Disjoint owned paths are scheduling constraints, **not a shell sandbox**. Overlapping writers require exclusive ownership; Git mutation and checkout-changing operations have a single explicit lease per workspace. Candidate freeze prevents mutations during review/checkpoint/measurement. Policy must deny conflicting dispatch before effects; delegation grants no tool permission.

A candidate reference is `{workspace_id, base_revision, head_revision?, focused_diff_digest, owned_paths, evidence_manifest_digest}`; uncommitted/shared candidates require the digest even when HEAD is known. Non-Git candidates use content manifest digests. ReviewId records reviewer, exact candidate, checks/evidence and disposition: `accepted`, `changes_requested`, `failed`, or `blocked`. Run completion is not review acceptance. `changes_requested` records a repair requirement; a separately authorized delegate/send creates a correlated new attempt and candidate, never rewriting earlier evidence. A changed candidate invalidates applicability of an earlier review, not its historical record. Acceptance never merges, stages, publishes or edits files implicitly.

## 3. Commands, revisions and receipts

Public schema version is `contract_version: 1`. Every mutation is an envelope:

```
{contract_version, command_id, kind, target, expected_revision, payload}
```

CommandId is caller-generated and stable across delivery retries. Expected revision is the target aggregate's revision; create uses an explicit `absent` precondition. Multi-owner operations (delegate, detach, review) carry all affected aggregate preconditions and commit atomically. IDs and selection are explicit in payload, not read from UI globals. Unknown schema versions/kinds reject without effects. Revisions are monotonically increasing per aggregate, not clocks. A successful command may update several aggregates in one transaction.

Domain canonicalizes the typed payload including target, version and preconditions; transport formatting is excluded. Dedup lookup precedes stale-revision checks: same CommandId and identical canonical envelope returns the original receipt/IDs without new events or effects, even if revisions have since advanced. Same ID with altered payload/target/precondition returns `command_id_conflict`, with zero mutation/effects. A new stale command returns `revision_conflict {current_revision}`; it cannot overwrite state. Rejected outcomes are durably deduplicated too. Command records remain available for the lifetime of referenced durable entities in v1; no expiring idempotency window is implied.

Receipt: `{command_id, outcome: accepted|rejected, reason?, entity_ids, committed_revisions, commit_sequence, effect_ids}`. `accepted` means durable intent committed, not runtime acknowledgment or completion. Rejected receipt has no effect IDs. An accepted mutation with no external effects has an empty list. Effect state/result queries and terminal events supply completion evidence separately. No transport timeout is evidence of rejection. Retrying delivery uses the same ID.

Each event has `{contract_version, event_id, commit_sequence, event_index, aggregate_id, aggregate_revision, kind, causation_command_id?, effect_id?, payload}`. `EventPosition = {commit_sequence: u64, event_index: u32}` is ordered lexicographically; indices start at zero within a committed transaction. Every public replay/snapshot/wait position uses this pair, never a bare transaction sequence. Query snapshot positions denote the transaction's final index; subscription batches return `end_position` for their final delivered event. Several events may share an aggregate revision: consumers deduplicate by EventId/position, not by revision equality, and must apply all unseen same-revision events. Revision checks detect stale state/gaps, not duplicate events. State and events commit atomically. Adapter observations retain runtime version and upstream event/request/turn IDs. Duplicate correlated observations never append duplicate content, charge usage twice or complete a task twice. An unrecognized uncorrelatable event records a bounded diagnostic and makes affected continuity unknown if necessary; it never manufactures success.

Core command vocabulary: `project.create`, `workspace.register`, `thread.create`, `thread.send`, `thread.reopen`, `approval.respond`, `run.cancel`, `run.reconcile`, `task.delegate`, `task.message`, `task.wait`, `task.cancel`, `task.detach`, `task.review`. Read-only inspection is `task.list`/queries. Send creates user MessageId, RunId, assistant MessageId and effect intent atomically. Reopen loads the same IDs/history without executing; explicitly continuing a terminal run uses a new send. Task send in the provider design maps to `task.message`, not an additional alias.

Required command payloads below are transport-independent records, not Zig/script bindings. `target` identifies the aggregate in the middle column; authorization is a trusted caller context, never a payload-granted role. All text/arrays have configured finite admission limits.

| Command | Target / required payload | Accepted result and normalized event |
| --- | --- | --- |
| project.create | absent / display name | ProjectId; ProjectCreated |
| workspace.register | absent / project ID, canonical binding, ownership policy | WorkspaceId; WorkspaceRegistered |
| thread.create | absent / project ID, workspace ID | ThreadId; ThreadCreated |
| thread.send | thread / source text or block references, selection, task ID if assigned | MessageIds, RunId, EffectIds; MessageAdded, RunQueued |
| thread.reopen | thread / none; read-only query, no mutation envelope required | Snapshot; no execution event |
| approval.respond | approval / decision allow or deny, exact scoped action digest | ApprovalResolved and optional reply EffectId |
| run.cancel / task.cancel | run/task / reason | CancelRequested; each actually needed cancel gets one EffectId |
| run.reconcile | run / saved session and effect references, optional explicit resolution evidence | RecoveryObserved, no start intent |
| task.delegate | parent task, or absent root / packet, source review ID for repair if any | TaskId, TaskDelegated, pending dispatch; root requires explicit user authority |
| task.message | task / content, delivery requirement queued or immediate | Domain-allocated MessageId, TaskMessageQueued; TaskMessageDelivered only on acknowledgment |
| task.wait | parent / nonempty unique child IDs, any or all, after-position, finite deadline | Waiter ID, TaskWaitRegistered; exactly one TaskWaitResolved result |
| task.detach | task / new durable owner, workspace lease transfer, budget allocation | TaskDetached; no new start |
| task.review | task / candidate reference, evidence/check references, disposition, reviewer context | ReviewId, ReviewRecorded; no repair start |
| task.list | parent / query filter, limit and cursor; read-only | Snapshot of children/results/reviews, no effects |

Root delegation creates the tree owner without invoking a runtime unless its packet explicitly requests a coordinator run. Child dispatch creates its thread/run under the same journal rules as send. Admission validates authority, immutable selection, workspace ownership and cumulative task allowance; runtime slots and request reservations are acquired only when pending work dispatches. A conflicting/busy workspace may remain blocked only if the accepted packet explicitly allows waiting; otherwise reject before intent.

## 4. Durable effects, approvals and recovery

Before any app-issued external action, domain commits an EffectId, type, immutable request digest, ownership, upstream correlation if known, and state `planned`. The dispatcher durably claims `in_flight` before calling the adapter. Normal states are `planned -> in_flight -> confirmed` or `failed`; uncertain delivery becomes `unknown`. A cancelled, provably non-dispatched intent instead becomes terminal `withdrawn`, with outcome `not_dispatched`, cancellation cause and one `EffectWithdrawn` event. Withdrawal commits atomically with cancellation and cannot be dispatched or converted back to planned after recovery. A claimed effect can withdraw only if serialized authorization evidence proves the external-call boundary was not passed; otherwise it remains unknown until reconciled. Only confirmed observations establish completed effects. Recovery dispatches only still-planned, uncancelled, validly owned effects, never withdrawn effects. Even upstream idempotency must be verified and capability-declared before relying on it.

Dispatcher rechecks durable cancellation/lease validity at the serialized authorization boundary immediately before the external call. If cancellation won before that boundary, withdraw the start and make no call; once authorization/call may have escaped, cancellation is best effort and recovery tracks ambiguity. A lease timeout alone cannot prove nonexecution or authorize another worker to repeat the effect.

Native runtime tools are not separately dispatched by the domain. Their observed call/action IDs and outcomes are durably correlated to the run; an app approval reply is journaled before granting permission, but this does not claim an app precommit before every opaque runtime-internal action. Runtime owns native tool execution, adapter owns reporting, domain owns authorization and ambiguity tracking. Lost tool results remain unknown; domain never repeats the native action to recover its result. Exactly-once external execution is not promised.

An effect can be confirmed while its run remains active: starting a turn is not completing that turn. Cancellation requests are separate journaled effects, not rollback. A late observation is correlated and retained even after cancellation; it cannot reopen a terminal run or silently erase a known external change. Irreconcilable late results remain flagged for review.

Approvals persist ApprovalId, run/session/tool correlation, exact action scope and workspace, policy source, status and expiry if any. Pending approval grants no authority. Only a revision-checked authorized response can schedule the adapter reply. Duplicate replies send once; an approval for a different action/session or after cancellation/expiry rejects. Restart may display pending approvals but cannot autoapprove. A response after reconnect requires positive evidence that the same upstream request is still live; transport-local callbacks cannot be restored from a saved ID. Otherwise invalidate the approval and reconcile, never fabricate a new approval or repeat the tool. Adapter cannot answer permissions from UI metadata.

Recovery inspects the durable journal and queries the same upstream session/turn when supported. `run.reconcile` can confirm recorded results, confirm no external action occurred, or retain unknown with evidence. Unsupported inspection/resume returns a capability result and preserves unknown. A human may resolve with explicit evidence and actor record; this is not a successful tool result. Creating a new attempt is a separate authorized command, warns about unresolved work and requires workspace ownership clearance. **Restart/reopen/reconcile never respawns unknown work.**

### Single lifecycle transition table

Run states: `queued`, `starting`, `streaming`, `awaiting_approval`, `cancel_requested`, `completed`, `cancelled`, `failed`, `interrupted`, `unknown`. Last five are terminal for dispatch; interrupted/unknown permit reconciliation only. Task execution uses `pending`, `running`, `cancel_requested`, `completed`, `cancelled`, `failed`, `blocked`, `unknown`; review disposition is separate. Every row commits its state/events before scheduling listed external actions. Event names below are normative normalized concepts, not upstream method names.

| Prior state / input | Committed state and event | External action / completion rule |
| --- | --- | --- |
| Absent project/thread; create | Entity revision 1; `ProjectCreated`/`ThreadCreated` | None. IDs survive reopen. |
| Idle/terminal thread; send with valid selection/lease | New messages + run `queued`; `MessageAdded`, `RunQueued`, planned start effect | No call until commit. Busy thread, unavailable capability, or unresolved effects without explicit ownership clearance rejects with no start effect. |
| Queued; dispatcher claims start | `starting`; `EffectClaimed` | Start exactly the journaled attempt. Start acknowledgment confirms only start effect, records session/turn mapping. |
| Starting/streaming/awaiting approval/cancel_requested/terminal; correlated content | `ContentAppended` at exact block offset; starting becomes streaming, awaiting approval stays awaiting, cancel_requested and terminal states stay unchanged | Persist valid contiguous late content for the same session/turn, deduplicated by observation/offset; never revive lifecycle, reauthorize tools or add a completion. Conflicting/gapped late content is retained as bounded diagnostic/recovery evidence, not blindly appended. |
| Starting/streaming/awaiting approval; permission request | `awaiting_approval`; `ApprovalRequested` | Track each request independently; no reply/tool authorization until policy responds. A request arriving after cancel is recorded invalidated and grants no authority. |
| Awaiting approval; authorized allow/deny | Approval resolved; `ApprovalResolved`, planned reply; run remains awaiting acknowledgment | One reply effect per approval; return to streaming only when no pending/live unacknowledged approvals remain. Deny may lead runtime to fail or continue, never guessed. |
| Nonterminal run/task; cancel | `cancel_requested` for dispatched work; invalidate approvals; `CancelRequested`, cancel effect only for dispatched work | Queued never-dispatched starts atomically become withdrawn/not_dispatched with EffectWithdrawn; run becomes cancelled with RunCancelled and no adapter call. Dispatched cancellation acknowledgment alone is not proof tools stopped. |
| Cancel requested; authoritative stop with known result | `cancelled`; `RunCancelled` (or `completed` with `cancel_too_late` if completion already established) | Preserve partial content/effects. No forced rollback. Unknown tool outcomes remain unknown, not clean cancellation. |
| Active; authoritative completion/failure | `completed`/`failed`; `RunCompleted`/`RunFailed`, completion evidence | Only known terminal outcome; task result records run and candidate, not automatic acceptance. |
| Any active; process exit/disconnect/crash | `interrupted` if no unresolved delivered effects, else `unknown`; `RunInterrupted`/`EffectUnknown` | No blind retry. Persist partial content; approvals stay pending or invalidated according to upstream evidence. |
| Persisted thread; reopen or UI reload | Same durable state; query snapshot (no lifecycle event needed) | None; no spawn, reauthorization, cancel or session replacement. |
| Interrupted/unknown; reconcile same work | Known terminal state, proven same active run, or still unknown; `RecoveryObserved` plus resolution evidence | Read/attach only when supported; active state restored only with exact session/turn and replay continuity proof, never a new start. Confirmed nonexecution ends interrupted; a new attempt needs a new command. |
| Pending/running task; child results in any order | Each child updated once; `TaskResultRecorded`; parent wait predicate recomputed | No automatic parent completion/review. Unknown child keeps subtree unsettled. |

## 5. Adapter seam and bounded delivery

The minimal **specified fake adapter**, to be implemented later, exposes the same semantic operations as real adapters:

- `discover` returns runtime/schema version and capability revision; each capability is `supported`, `unsupported` or `unknown`, with constraints/evidence. Unknown is not supported.
- `accountStatus(account_ref)` and `resolveSelection(selection)` report readiness and effective identity without credential export. Fake identities are synthetic.
- `openSession(workspace, selection, existing_session?)` either creates under a journaled effect or attaches to the exact existing session; attach cannot fall back to create.
- `start(effect_id, session, run, prompt)`, `respondApproval(effect_id, approval, decision)`, `cancel(effect_id, run)` and capability-gated `message(effect_id, run, message_id, content)` accept correlated requests. Adapter receipts mean delivery/acknowledgment only. Unsupported immediate message delivery rejects; explicitly queued messages remain visible without starting replacement work.
- `inspect(session, turn/effect)` and `attach(session, after_upstream_cursor)` report terminal/active/unknown and replay continuity if supported; no hidden restart.
- A bounded observation stream emits selection/session acknowledgment, content blocks, tool lifecycle, approvals, usage, completion, disconnect and explicit errors. Fake scripts control these observations, duplicates, reordering, crash boundaries and unknown outcomes deterministically. It need not execute tools, auth or inference.

Capability keys include session create/attach/resume, streaming, tool observations, approvals, cancellation, outcome inspection, replay continuity, model/effort selection and verification, usage dimensions, coordinator bridge, and workspace binding. Each is version/transport/account-scoped; a supported general runtime does not imply all keys. Callers requesting a required unsupported/unknown capability receive `capability_unavailable` before new effects. Lost capability mid-run marks affected work interrupted/unknown rather than pretending completion. Basic conversational support and coordinator eligibility are distinct gates.

Configure finite byte/frame limits, pending-request count, observation queue bytes, decoded page bytes, chunk size and subscriber lag before admitting an adapter. Adapter framing checks occur before allocation; oversized frames yield explicit failure/unknown continuity. Stream chunks append to durable content once; views reference blocks/offsets rather than copying entire transcripts on each delta. Apply transport backpressure when supported; otherwise spool within bounded durable quotas or interrupt explicitly at quota. Never drop canonical text or Unicode bytes to keep a UI fast. UI presentation may split work across frames, not alter original content. Approval/completion ordering is preserved. Unknown optional events can be diagnosed in bounded form; no unbounded raw payload log is required.

## 6. Query/subscription seam

`query(kind, filter, limit, cursor?)` returns `{snapshot_id, snapshot_position: EventPosition, items, next_cursor?, expires_at}`. Kinds include projects, threads, messages/content ranges, runs/effects/approvals, tasks/results/reviews and capabilities. Limits have finite server maxima; history remains on disk. Rows contain stable IDs/revisions, not mutable array indices. Content queries return exact source ranges and continuation offsets, not eagerly decoded whole histories. No query starts or cancels work.

First page fixes ordering/filter and a bounded-lifetime snapshot. Opaque cursors bind snapshot, ordering, filter and last stable ID; page two must observe that snapshot, not a mixture with current data. New writes notify `newer_revision` but do not invalidate an otherwise retained snapshot. Expired/evicted snapshots return `cursor_invalid {reason, refresh_required:true, anchor_id?}` with no mixed page. Invalid filter/cursor pairing also rejects. Refresh starts a new snapshot anchored to a stable ID; if deleted, report missing anchor and explicit nearest ordering boundary. Never silently jump by numeric index.

`subscribe(scope, after_position: EventPosition, max_batch_bytes)` replays retained committed events strictly after that pair, then tails. It returns bounded batches with `end_position: EventPosition`, including when a batch splits a transaction. Resume from that exact pair, not the transaction's final index. The query-to-subscription seam cannot lose commits between calls. Delivery is at least once in position order; deduplicate EventId/position, never discard an unseen event merely because its aggregate revision equals the previous event's. If history is not retained or a subscriber queue overflows, emit `resync_required` and stop deltas until a fresh snapshot; never silently skip. Unsubscribe/reload releases ephemeral buffers only. UI catches up from snapshot_position and stale buttons still carry expected revisions. Invalid config retains the last working root; stale callbacks reject while accepted commands survive disposal.

## 7. App-owned delegation and coordinator bridge

`task.delegate(parent_id, packet, expected_revisions)` allocates one child TaskId and dispatch intent atomically; duplicate command returns the same child. Parent must have coordinator authority and capacity. V1 defaults: two concurrently executing descendants per root (detached descendants still consume the original root's slots), depth one (children cannot delegate), finite task/request/time limits; configuration can lower limits. No unlimited value or recursive fan-out in v1. A third child may be durably pending but starts only after a slot and budget reservation are available.

`task.message(task_id, content, delivery_requirement)` durably enqueues a domain-allocated MessageId; receipt is not delivery or a new run. Delivery/consumption is separately recorded. Unsupported immediate steering rejects; explicitly queued messages remain pending, never simulated by interrupt/restart. `task.wait(parent_id, child_ids, mode:any|all, after_position: EventPosition, deadline)` registers a durable bounded waiter with a stable result and `resolved_position: EventPosition`; no busy polling. It first evaluates current outcomes, so results before registration are not missed; after_position is a replay position, not permission to ignore existing terminal results. Terminal outcomes including unknown satisfy the waiter, while unknown effects/budgets remain unresolved. Return all matching outcomes through resolved_position; later completions stay queryable. Timeout never cancels children. `task.cancel` uses the lifecycle table; `task.list` uses the query snapshot contract and distinguishes app/native children.

Concurrent child results are serialized as domain commits, each keyed by child/run/result identity. They cannot overwrite each other or each other's candidate/review. Wait predicates are evaluated in the committing transaction. Native runtime children are observations only unless explicitly mapped; they are not redispatched or counted as additional app children.

Parent cancellation propagates to all attached descendants and withdraws pending starts atomically. Cancellation races with child completion preserve whichever known outcome actually occurred. `task.detach` requires explicit authorized new durable owner, workspace lease handoff and budget reservation; it is not UI closure. Detach must commit before parent cancel to escape propagation; stale racing detach rejects. Detached work retains ancestry for cumulative accounting and has its own lifecycle/cancellation owner. No orphan work without an owner.

Budgets are persisted at root and reserved before dispatch: cumulative task count, concurrent slots, request count, deadline/wall time and supported usage/cost dimensions. Reservations and charges are atomic across the observable subtree, including repairs, detached descendants and reported native work without double-counting their inclusive usage. Spent budget never refunds on completion/cancel; unused provably unspent reservations can release. Usage records are keyed by upstream run/report identity and replacement revision, with explicit inclusive/exclusive accounting; repeats do not add spend. Unknown inclusive attribution is labeled incomplete, not summed speculatively. A descendant cannot detach to reset its root allowance. Exhaustion prevents new effects and requests cancellation where policy requires; already unknown work keeps its reservation until reconciled. Deadlines use persisted elapsed/deadline evidence, not reset-on-restart timers.

The cumulative task allowance counts descendant TaskId allocations only; root R establishes the allowance and does not consume one unit. Every new descendant/repair TaskId consumes one permanently, including detached descendants; another run on the same TaskId consumes request allowance but not a second task allocation. Native observed children do not consume app TaskId allocation allowance, but their observable generation/usage remains in the request/usage budget. Thus allowance three permits root plus three app descendants, four TaskIds total, not four descendants.

App-observable request allowance counts generation starts (including repairs and any observable native generation), not transport housekeeping; message delivery that starts generation must reserve a request too. Cancel, deny and read-only reconciliation remain available at exhaustion and cannot start replacement work. Deadline enforcement is a hard cutoff for new dispatch, not a guarantee an opaque tool stops at that instant. Token/request usage inside opaque runtimes and currency/subscription costs can be estimated, delayed or absent. Report `{measured, reserved, unknown, enforcement:hard|best_effort|unavailable}` per dimension. If a packet requires a hard bound the runtime cannot observe/control, reject before dispatch; never claim subscription billing accuracy. Model mismatch and exhausted budget are visible stop reasons.

Coordinator bridge requirements: a version-supported structured host-tool or MCP hook must expose delegate/message/wait/cancel/list to the **running coordinator session**, bind calls to its TaskId/authority, preserve caller/tool-call dedup IDs, validate schema and route responses to the originating call. Prompts and terminal-text scraping do not supply this bridge. Tool cancellation/disconnection cannot undo accepted durable commands; redelivery resolves the same receipt. Bridge credentials are scoped to permitted tasks/commands and cannot bypass workspace/approval/budget checks. Exact runtime hook evidence and remaining uncertainties are in [references](references.md); adapter milestones must prove registration, invocation, correlated response, cancellation and reconnect against their pinned executable/schema before advertising `coordinator_bridge=supported`. No live bridge or adapter is asserted here.
